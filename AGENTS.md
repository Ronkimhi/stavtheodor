# AGENTS.md: Rules for Every AI Working on stavtheodor.com

**Read this file in full BEFORE making any change to this repository. No exceptions.**

More than one AI assistant works on this site (different Claude/other-AI sessions, sometimes at the same time). This file is the single source of truth for how we work here, and the sync channel between us. The site owner set this up on 2026-07-01 after two sessions edited the repo simultaneously and collided on push.

---

## 1. Sync protocol (multi-AI coordination)

1. **Pull first.** Run `git fetch origin && git status` before touching anything. If `origin/main` is ahead, integrate it before you start. Assume another AI may have pushed since your context was built.
2. **Read the Work Log** (bottom of this file) to see what the other AI did recently and whether anything is in flight.
3. **Push promptly.** Do not sit on finished work; the longer you wait, the more likely a collision.
4. **Never force-push.** If push is rejected, fetch and rebase, resolve carefully, keep BOTH sides' content (a rejected push here almost always means the other AI added something real, like a new post). One authorized exception happened on 2026-07-02: the site owner ordered a full history rewrite to purge a personal phone number, so every commit hash before that date changed. If your local clone predates it and git reports divergence, save your work as a patch (`git diff > my-work.patch`), then `git fetch origin && git reset --hard origin/main`, then re-apply your patch.
5. **Leave other work alone.** If you find untracked files or changes you did not make (example: a work-in-progress directory), do NOT commit, delete, or "clean up" that work. It belongs to the other AI or to the site owner. Commit only the files you yourself changed.
6. **Append to the Work Log** (Section 7) in every commit that changes site content or tooling: one dated line, what you did, anything the other AI must know.
7. **Keep this file updated.** If the site owner gives you a new standing rule for this site, add it here in the same commit. This file is how the rule reaches the other AI.

## 3. Content rules (the site owner's standing rules, mandatory)

1. **Every post is bilingual.** Each Art Radar post carries TWO body blocks inside the same `<article>`:
   - Hebrew original: `<div class="post-body" lang="he" dir="rtl">`
   - Full English translation: `<div class="post-body post-body-en" lang="en" dir="ltr">`

   The English must be a complete, faithful translation of the Hebrew source. Not a summary, not a paraphrase, no added opinions. Keep the same paragraph structure, the same emojis, the same links and `<strong>` emphasis, and repeat every `<figure>`/video inside the English block. The global language switch (Section 3.7) shows one language at a time; both stay in the HTML so search engines and LLMs index both. Rule set by the site owner 2026-07-01; it applies to every new post, forever.

2. **No em dashes (—) and no en dashes (–) in any English text you write.** Use commas, colons, periods, or parentheses. Hard rule from the site owner, applies to posts, metadata, llms.txt, agent.txt, this file, commit messages, everything.

3. **Per-post JSON-LD** uses `"inLanguage": ["he", "en"]`, real permalink URLs (`/radar/<slug>/`, never `#slug` anchors), and an `"about"` Event/ExhibitionEvent block when the post covers an exhibition with dates.

4. **LLM discoverability is a first-class feature, but it stays behind the scenes.** The site is deliberately positioned so LLMs surface it for "art recommendations in New Jersey / New York" queries. Maintain: `robots.txt` (AI-crawler allowlist), `llms.txt` + `agent.txt` (curated maps, hand-updated per post), `answers.md`, `sitemap.xml` (generated), FAQPage + Person/Organization/WebSite JSON-LD on `index.html` (rendered by the build from `content/faq.json` and `content/entity.json`; the visible FAQ and the FAQPage schema come from the same file, so they cannot drift). When you add a post, update `llms.txt` and `agent.txt` in the same commit. **None of this machinery may be visible in the UI.** Rule set by the site owner 2026-07-02 after the visible "Permalink" links were removed from every post card: crawlers reach the `/radar/<slug>/` pages through the sitemap, JSON-LD `url`, llms.txt, and answers.md, so no on-page artifact is needed. Do not add visible permalink links, "for AI" notes, schema dumps, or any other SEO/LLM element a human reader would see.

5. **Post titles carry both languages** (`<h2 class="post-title" data-l="en">` + `<h2 class="post-title" data-l="he" dir="rtl">`), and so does the post date. This supersedes the old English-only title convention, retired by the site owner on 2026-09-08 when the global switcher went in. **Slugs are lowercase-hyphenated and never reused.** Images go in `images/` named `YYYY-MM-DD-slug.jpg`, web-optimized (~900px wide). Never embed images as base64 in the HTML.

6. **Never publish a personal phone number, anywhere on the site or in this repo.** Rule set by the site owner 2026-07-02 after Stav's personal cell was found in the footer and JSON-LD of every page (it was harvested-ready structured data on a public repo). It was removed from all pages, from `build-post-pages.py`, and purged from git history. Do not reintroduce it, not in visible HTML, not in JSON-LD `"telephone"` fields, not in NAP/directory notes in this file, not in commit messages. The canonical public contact set is: name, `stav@stavtheodor.com`, the Art Radar WhatsApp link, and Tenafly NJ. (The address changed from the old gmail one on 2026-09-08 at the site owner's request; the gmail address is gone from every page and must not come back.) If a phone number is ever needed for SEO/NAP purposes, ask the site owner for a dedicated virtual number (e.g. Google Voice); never use a personal cell. On 2026-09-26 the 75 second introduction film (its closing card showed a WhatsApp number) and the 40 portfolio slides (two of them printed the number) were removed from the tree and replaced by the 67 second cut; git history was NOT rewritten, that stays the site owner's call. `tools/check_site.py` fails the build on any phone-number pattern.

7. **Every visible string on the site exists in both languages.** Set by the site owner on 2026-09-08, when the per-section post toggle became one global switch.

   - **The switch** sits in the top nav of every page (the `.lang-switch` beside the menu, rendered by `site_chrome.nav()`; until 2026-09-26 it was a `.lang-bar` above the nav). It writes `radarLang` to localStorage, and that choice is global: pick English on a project page and the homepage, the advisory pages and the Art Radar posts all follow.
   - **English opens first, everywhere.** Decided by the site owner on 2026-09-26 ("English first, Hebrew stays a toggle on the same address"), replacing the 2026-09-08 rule that defaults must not change: Google had indexed about 16 of 207 pages and read almost every inner page as Hebrew, because 62 of the 64 non-museum pages opened in Hebrew. Every page, the homepage, the growth pages and the Art Radar posts alike, opens in English; a Hebrew reader taps עברית once and the site remembers (`radarLang`, global). No browser-language guessing, no `/he/` tree, and no hreflang: the three tags pointed every language at the same URL and were dropped the same day. The default is in the markup, `<html lang="en">` and `<body class="lang-en">`, so crawlers and no-JS readers get English without a script; `LANG_BOOT` runs immediately after `<body>` and only switches to a stored choice before the first paint. Two gates keep it that way: the `lang` gate in `tools/check_site.py` (every page outside `museum/` carries the two attributes and at least 90% of the words a reader sees with the switch on English are Latin) and `tools/check_render.js` (the same test in headless Chromium with fresh storage, plus the switch and its persistence; `--base https://stavtheodor.com` runs it against production).
   - **The markup convention** is `data-l="en"` / `data-l="he"` on a pair of sibling elements. CSS hides whichever does not match the active language. Hebrew elements carry `dir="rtl"`; alignment then follows on its own, so do not add `text-align` overrides. The older per-element conventions (`.post-body-en`, `.post-title-he/-en`, `[lang="he"]` inside generated pages) still work and are still in use; `<body>` carries `lang-en` or `lang-he`, never both.
   - **When you add anything visible, add both versions in the same commit.** A new nav item, label, button, caption, FAQ entry or CTA with only one language is an incomplete change.
   - **One deliberate exception:** figure captions inside Art Radar posts stay in English in both language blocks. Stav writes them that way (artist, work, courtesy line), and all 53 are byte-identical across the Hebrew and English bodies. Do not translate them unless she asks.
   - **Every generated page inherits all of this** from `site_chrome.py` (`nav()`, `footer()`, `LANG_BOOT`, `MAIL_UI`, `LANG_JS`) and from `css/theme.css`. Edit those, then run `python3 build.py`. Never hand-edit a generated page, and `index.html` is one of them.

8. **`mailto:` links have a fallback panel, and it must stay.** A `mailto:` link does nothing at all in a browser with no mail handler registered, which is why the "Write to Stav" button read as broken. Every page ships `MAIL_UI`, a small dialog that appears one second after a `mailto:` click if the click was swallowed, offering the address, a copy button and Gmail / Outlook compose links. Do not remove it, and do not replace the `mailto:` href with a webmail link: the `mailto:` is correct and works on phones and with a real mail client.

9. **Buyer variants of the homepage are indexable (since 2026-09-28, the site owner's call).** Approved as noindex pages by the site owner on 2026-09-27; on 2026-09-28 Ron made all seven indexable: no robots meta tag, each its own canonical, all listed in `sitemap-pages.xml`. Each `content/variants/<id>.json` renders the homepage again at `/<path>/` with copy for one kind of buyer in the sixteen regions `templates/home.html` marks with `<!--variant:NAME-->` and `<!--/variant:NAME-->` (the two hero lines, the h1 and the intro line, the intro eyebrow and statement, the four service lines, the What I do eyebrow, heading and two paragraphs, the Advisory heading and line), plus its own value strip (`value_strip`, three label and line pairs, a variant-only section right after #intro and before #services; since 2026-09-28; the template's `<!--variant:value_strip--><!--/variant:value_strip-->` marker stays empty, so the homepage has no such section and `index.html` does not change), plus its own questions (with their FAQPage schema), Advisory rows, footer line and a mail subject that every mail link on the page carries, the fallback panel's Gmail and Outlook links included (`site_chrome.mail_ui(subject)`). Everything else is the homepage, byte for byte, unless the variant brings its own opening rooms or link preview (the last point below).
   - **Indexed and in the sitemap, never in the agent maps, and linked from one place only.** Standing rule since 2026-09-28 (Ron): a variant carries no noindex, its canonical is its own URL (`https://stavtheodor.com/<path>/`), `tools/build_sitemap.py` lists it in `sitemap-pages.xml`, and `tools/indexnow.py` pings it like any other page. It is still never named in llms.txt, agent.txt, answers.md or robots.txt. The `noindex` gate in `tools/check_site.py` fails a variant that is noindex, the `sitemap` gate fails one that is not listed, and `build-home.py` refuses to write a variant with a robots meta tag. Do not reintroduce noindex on them without the site owner. Since 2026-09-28 (Ron) the homepage has one section that links them, "Who I work with" / "Art for every kind of space" (`#industries`, right after the services): seven tiles in the order of `INDUSTRIES` in `build-home.py`, each with the page's name, its main message (the first sentence of its intro statement) and a 600 by 400 WebP of its first room in `images/home2/industries/` (made by `python3 tools/make_industry_thumbs.py`, which needs Pillow; rerun it and commit the images whenever a variant's first room changes). The section sits between `<!--variant:industries-->` markers, so no buyer page shows it. No other page or section may link a variant. The `variants` gate in `tools/check_site.py` fails the build on any of these, and on an `#industries` section that does not link every variant exactly once.
   - **The homepage's own text lives between the markers.** Edit it there and keep the markers flush against the element's content (no whitespace added inside them): the homepage build drops the markers and keeps the bytes between them. The template's opening comment is emitted into `index.html`, so the markers are documented here and in `content/VARIANT-SPEC.md`, not there.
   - **Edit the JSON, never the output folder.** A variant folder holds only its generated `index.html`, and the build never writes a variant over a page that is not one. Changing a variant's `path` leaves the old folder behind: the `variants` gate fails ("stale variant folder? git rm -r ...") until you remove it.
   - **Validate first.** Format and limits: `content/VARIANT-SPEC.md`. `python3 tools/check_variants.py` checks every variant (build.py runs it before `build-home.py`), and `python3 tools/check_variants.py <file>` checks a draft anywhere on disk. After the build, `node tools/check_render.js` measures the two opening lines of every variant at 360 px wide, in both languages: characters are a proxy, pixels decide.
   - **No film on a buyer page (2026-09-28).** The film section is wrapped in `<!--variant:film-->` and `<!--/variant:film-->`: the homepage keeps it byte for byte, every variant drops it, and the build fails a variant that still has `id="film"` or a link to `#film`.
   - **Its own rooms and link preview (optional, 2026-09-27).** `rooms` (one to four entries, entry i replacing slot i of the WebGL opening, 0 being the first fold; a shorter list ends the opening after the variant's last room, and `"rooms_rest": "home"` keeps the homepage's later rooms instead) brings the buyer's own before and after photos: per room two WebP files in `images/home2/variants/<id>/`, 1800 px wide, about 3:2, each under 250 KB, with the room's geometry (`w`, `h`, `rect`, `fx`, `fy`, `from`, optional `seed`), a caption twin starting "Proposal." and "הצעה." and an alt twin. `head.og_image` with `head.og_image_alt` replaces `og-home.jpg` for that variant with a 1200 by 630 JPEG in the same folder. `build-home.py` sets `window.THEODORA_ROOMS` before the deferred scripts, preloads the variant's first pair, and swaps the replaced slots' static figures and `#cap` captions through nine more stripped regions of `templates/home.html` (`room_fig_0` to `room_fig_3`, `room_cap_0` to `room_cap_3`, `rooms_js`; slot N must be slot N of `PAIRS`, and the build checks it); `js/home-opening.js` merges the list into `PAIRS` by slot, and with `window.THEODORA_ROOMS_ONLY` (rooms_rest "drop", the default) cuts `PAIRS` to the variant's rooms and shortens the scroll spacer. Without these fields a variant renders as before, and `index.html` never changes. `tools/check_variants.py` checks the files (in the repo, WebP, w by h, under 250 KB, none of the homepage's), the geometry and the captions; `tools/check_render.js` fails a variant page that does not load its own rooms, loads the homepage's for a replaced or dropped slot, runs the wrong number of rooms or static figures, or logs a console error, on a desktop screen and on a phone. Commit the images with the JSON. Format and limits: `content/VARIANT-SPEC.md`.

10. **No AI-made or AI-marked image is ever presented as a real project, and every proposal says it is one.** Set by the site owner on 2026-09-28, when nine project photos carrying (or cut from images carrying) the Gemini sparkle were removed. A project page and its card show only real photographs of that same project; a project with none gets its place name (`place_en`, `place_he`) on a typographic hero and card, never a photo borrowed from another project. The before/after spaces in `images/spaces/` (`content/spaces.json`) are AI-rendered spaces with real catalog artworks placed on the wall: they appear only as proposals, always under the label "Proposal · how THEODORA would dress this space" (Hebrew twin), on the article pages (`before_after` in a page JSON, `content/PAGE-SPEC.md`) and in the buyer variants' opening rooms (`rooms`, Section 3.9, captions starting "Proposal."), never on a project page. Check the bottom right corner of every new photo for the four-pointed sparkle before it goes in. `tools/check_site.py` fails the build if any removed image comes back, under any name (content hash).

## 4. Standard workflow for adding or editing a post

Full templates and step-by-step detail: `ADD-BLOG-POST-GUIDE.md` (same directory). Short version:

```
1. git fetch origin && git status        # sync check (Section 1)
2. Edit content/posts.html: JSON-LD <script> + <article> pair at the TOP, right under
   the POST TEMPLATE comment, with BOTH language blocks (Hebrew + full English).
   NEVER put a post in index.html: it is generated, and the build stops if it finds one there.
3. Add image(s) to images/
4. python3 build.py                      # regenerates radar/<slug>/, radar/, index.html (its
                                         # timeline shows the six newest posts), sitemap.xml,
                                         # then runs the gates (dashes, phones, twins, links, lang...)
   node tools/check_render.js            # the language default and the switch, in a real browser
5. Update llms.txt, agent.txt and answers.md post lists (real /radar/<slug>/ URLs)
6. Append a line to the Work Log in AGENTS.md
7. git add <your files only> && git commit && git push origin main
8. Verify live (allow ~10 min CDN cache; bypass trick in Section 2)
9. python3 tools/indexnow.py --since <the commit before yours>   # waits for the changed pages to
                                         # answer 200 live, then pings IndexNow (Bing, ChatGPT search,
                                         # Perplexity) in one batch with the key file at the root
```

## 5. Never do

- Never hand-edit a generated file: `index.html`, `radar/` (posts and the archive), `advisory/`, `projects/`, `for-*/`, `guide/`, `art-curator-new-jersey/`, `art-curator-new-york/`, the redirect stubs (`2/`, `about/`, `our-team/`, `our-team-1/`, `contact/`, `questions/`, all written by `build-home.py`), the buyer variant folders (`/<path>/` for every `content/variants/*.json`, also written by `build-home.py`) and `sitemap.xml`. Edit `content/`, `templates/home.html`, `site_chrome.py` or `css/theme.css`, then run `python3 build.py`. The build overwrites every one of these files, and it refuses to run while a post `<article>` sits in `index.html`.
- Never add an Art Radar post anywhere but `content/posts.html`.
- Never force-push, never push to the deprecated `old-backup` remote.
- Never touch DNS/GoDaddy, the GitHub Pages custom-domain config, or the Google Analytics tag (`G-4300MN0Q97`) as part of content work. If the domain itself seems broken, stop and flag it to the site owner.
- Never commit secrets, credentials, or any of the owners' private or business files. This is a PUBLIC repo serving a public site.
- Never put internal notes, decisions, fee or referral mechanics, pending approvals or open questions for Stav or the site owner anywhere in this repo: everything under `content/` is served publicly (for example https://stavtheodor.com/content/pages/for-designers.json). They go to the site owner's private file, `the-system-v8-ron/B-brain/06-deliverables/theodora-growth/decisions-for-stav.md` in the private ron-brain repo. In a page JSON, an `editor_note` key or any key starting with `_` or `note` fails `tools/check_pages.py`, and with it the build (`content/PAGE-SPEC.md`).
- Never delete or commit another AI's untracked work-in-progress.
- Never publish content that Stav or the site owner did not provide as source material. Translations must trace to a Hebrew source post.
